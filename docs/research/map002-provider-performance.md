# MAP-002 V3.1 · Provider 负载验证（进行中）

X300 Pro / Android 17，普通应用、主卷用户授权图片；应用只读，无后台轮询、无并发压力测试。最近 500 个 ID 的一次 Provider 查询及遍历耗时 10 ms；包括目录计数、两个 Provider 查询、缩略图读取的整个任务耗时 74 ms。100 张的整次任务 102 ms。各仅一次实测，不能比较为规模趋势，也不是 P50/P95 或峰值。

500 条查询后，测试应用 `dumpsys meminfo` 报告总 PSS 约 30,505 KiB；这是事后快照，不是峰值，不可归因于某次查询。观察到的 vivo 相册进程在查询前后仍存在；这不能证明无卡顿、锁等待、ANR 或服务负载。

仍缺：原生相册空闲和用户浏览时的成对基线、相册处理新照片期间的对照、长短视口查询的独立耗时和返回规模、取消是否被 Provider 真正响应、退出清理、CPU 峰值与内存峰值、锁等待和 ANR、全库访问策略。应用发出 10 秒取消请求，但系统 Provider 如果不响应不能保证硬超时。已有目录约 7.9 万张；不要通过高频小批量查询来推测或替代全库安全验证。当前证据不足以认定负载满足正式应用要求。

## 原生相册前台浏览时的单次试验

用户让 vivo 相册保持前台并正常浏览时，以一次性后台广播启动单 worker 查询；系统前台 Activity 确认为 vivo 相册。最近 2,000 张授权图片 ID 中，Provider 返回 1,998 个唯一同 ID 项、2 个未匹配；返回项 MIME 1,998 个相同，GPS 非零且在数值范围 1,864、空值 134。Provider 一次查询与遍历 17 ms；包含目录计数、Provider 范围复查和缩略图的任务 121 ms，应用 worker 线程 CPU 18 ms；不含 Provider 进程 CPU。用户随后表示查询期间没有察觉明显异常。完整脱敏日志：`evidence/MAP-002-v31-readonly-2000-gallery.txt`。

这是一次短查询和一次主观观察，不证明不存在锁等待、ANR、峰值或原生相册后台处理期间的影响，也不证明全库访问可接受。未匹配两条可能尚未建立扩展记录、失效或存在其他原因，尚未复核，不得直接解释为无 GPS。

20,000 项一次有界 ID 查询及遍历单次 98 ms；之后三批分别 102、103、87 ms，目录计数与各批总工作耗时约 184、235、240、228 ms。每批间隔约 5 秒，为一次性覆盖统计；不是地图操作时持续查询的推荐策略。未同时采集 Provider 独立 CPU、锁等待或内存峰值，因而不能据此认定全量访问对相册无影响。

补测中预先取消查询返回 `OperationCanceledException`，不代表运行中的 Provider 查询响应取消；无效投影触发异常后，同一进程一次正常样本查询成功。尚未测量真实超时、运行中取消、Cursor 服务端释放或负载峰值。参见 `evidence/MAP-002-v31-wrap-cancel-error.txt`。

## 遍历取消与退出合并试验

2,000 ID 的只读查询返回 Cursor 后，在第一行遍历时主动取消；客户端检测到取消，Cursor `isClosed()` 为 true。同一进程随后以 500 ID 运行正常查询、普通视口和跨日期变更线范围比对，并成功读取一张缩略图。另一次测试人为在首行暂停最多 3 秒，在 Cursor 打开时通过返回键退出探针 Activity；约 1 秒后记录取消异常及客户端 Cursor 已关闭。日志仅含聚合结果：`evidence/MAP-002-v31-cursor-exit.txt`。

该测试覆盖的是查询已返回后的客户端遍历和 Activity 正常销毁；不能证明 Provider 远端 SQL 执行期间可中断、远端游标或锁何时释放，也不覆盖强制终止、ANR 和无响应 Provider。等待仅作为单次受控诊断，不用于正式查询策略。

## 进程内数组加载与视口试验（2026-11-24）

在单主卷、完整图片授权的 X300 Pro 上，探针先分别读取 200、2,000、20,000 个 MediaStore 可见 ID，以受限 ID 查询 Provider，将数值有效且非零的坐标保存在基础类型数组中。2,000 项的加载总耗时 106 ms、Provider 查询遍历 34 ms；20,000 项分别为 226 ms、157 ms。这是各一次试验，不代表冷启动分布。两组内存视口与同批受限 Provider 查询结果分别一致，后者独立查询耗时 8 ms 和 45 ms；这不是无 ID 限制的全库视口比较，也不能外推重复地图交互的服务负载。`evidence/MAP-002-v31-load-samples.txt`。

随后一次前台完整读取 79,147 个可见 ID：4 次 Provider 查询及遍历分别 54、68、64、85 ms，共 271 ms；79,144 条返回、3 条缺项、69,637 条坐标入数组。加载总耗时 15,482 ms，包含 3 次各 5 秒的主动批间间隔，且包含 MediaStore、应用处理和内存采样。数组最大容量 100,000，四个主要基础类型数组总载荷 3,200,000 字节，另有临时 ID 副本、选择参数、Cursor 和运行时开销；容量超出时完整加载试验停止。应用 PSS 在加载前和各批结束时采样为 88,613 至 89,084 KiB，不能代表真实峰值或直接归因于数组，也不能与不同应用状态下的测量直接比较。局部数组在方法退出后不再由该方法持有，但并未证明垃圾回收立即发生。结果仅在内存中，未发布给地图或持久化。`evidence/MAP-002-v31-memory-full.txt`。

为合并观察原生相册浏览影响，用户保持相册前台并正常浏览，后台一次性广播开始同样的分批加载；只观察到前两批（各 20,000 ID，84 和 49 ms），之后探针未继续输出，原因未确认，可能是后台冻结。为避免以后意外继续，随后停止探针；因此无完整后台结果。用户对已经运行的部分反馈没有察觉明显异常。相册进程一次中途 PSS 快照为 1,523,349 KiB，当时用户正在浏览，无法归因于本次查询，也不是峰值或锁等待证据。

另一次前台对 20,000 ID、17,662 个内存坐标运行范围筛选：普通视口 78 条，重复筛选 78 条，更大重叠视口 634 条；单次扫描分别约 633 和 591 微秒。真实数据中所选 ±180° 窄范围为 0 条，不能证明真实跨线覆盖；在同一手机进程中运行的合成坐标样本覆盖了 ±180° 和跨线边界。世界范围计数与载入数一致。上述重复和重叠检查是数量关系，不是所有结果 ID 的独立正确性证明；未执行聚合或持久化。`evidence/MAP-002-v31-memory-range-gallery.txt`。

这些结果支持继续研究内存加载，但不证明位置身份、同进程权限变化、远端取消、应用/相册的峰值内存或 CPU、锁等待及全库视口方案已通过验收。

CPU 对照尝试：在相册前台浏览时测量相册进程 CPU 和 PSS，并发送一次 2,000 ID 的后台广播。但所需时间窗内没有出现本次查询完成日志；初版脚本误选了之前 20 ID 的旧日志，随后已核对时间戳并标记该轮无效。已停止测试探针以避免广播延迟执行。无法将两段 CPU/PSS 数值解释为查询负载对照；见 `evidence/MAP-002-v31-gallery-cpu-sample.txt`。

CPU 对照重试前先在前台唤醒探针，再由用户切回相册浏览；以触发时刻和本次探针 PID 限定日志，测量窗口内仍未观察到 2,000 ID 查询完成，因此该轮同样无效。脚本在首次重试时因设备日期命令参数错误提前终止，尚未发送查询；修正后的一次广播未在窗口内完成。随后已停止探针，避免延迟运行。不能把两段 CPU 或相册 PSS 差值归因于查询。见 `evidence/MAP-002-v31-gallery-cpu-retry.txt`。

后台诊断补充：试用仅用于测试的短时前台服务，并在用户浏览相册时尝试触发一次 2,000 ID 查询；无论通过广播还是在服务内部定时启动，测量窗口都未观察到本次查询开始或完成日志。进程调度或服务生命周期的实际原因未知，不能将 CPU 或 PSS 差值归因于查询；两次均已停止探针。诊断服务及权限已从源码撤回，不作为正式方案。日志 `evidence/MAP-002-v31-gallery-cpu-foreground-service.txt`、`evidence/MAP-002-v31-gallery-service-scheduled.txt`。
