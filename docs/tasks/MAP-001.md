# X300 Pro vivo 相册 GPS 数据与足迹地图接口逆向调查

| 项目 | 内容 |
| --- | --- |
| 任务编号 | MAP-001 |
| 任务类型 | 技术预研 / 本地设备调查 / 只读逆向分析 |
| 执行环境 | Windows + Codex Desktop + ADB |
| 目标设备 | vivo X300 Pro（V2502A） |
| 目标系统 | 设备当前安装的 OriginOS 版本，以 ADB 检测结果为准 |
| 优先级 | P0 |
| 当前状态 | 待执行 |

本任务仅开展调查、只读验证和技术方案评估。地图相册正式开发须在提交最终技术报告和推荐架构后，由用户确认启动。

## 一、任务背景

计划开发一款独立 Android 地图相册应用，读取手机已有照片，并按拍摄位置在地图上展示。现有照片数量较多，优先调查 vivo 原生相册是否已经建立 GPS 索引，以及第三方应用能否合法、稳定地复用该索引，避免再次完整读取所有照片的 EXIF GPS 信息。

1. 确认 vivo 足迹地图的 GPS 数据来源。
2. 确认 vivo 相册是否使用独立媒体数据库。
3. 查找地点、GPS 与照片的关联索引。
4. 查找对外提供查询的 Android ContentProvider。
5. 查找系统级媒体扩展服务。
6. 评估合法、稳定的复用方式。

## 二、调查原则

- 所有调查在本地 Windows 电脑开展，由 Codex Desktop 执行 PowerShell、ADB 和本地 APK 分析工具，无需用户逐条运行命令。
- 优先使用 Android 官方接口和 vivo 已公开接口。
- 保持手机系统和 vivo 相册文件原样，禁止 Root、解锁 Bootloader 或绕过应用沙盒、签名权限和访问控制。
- 禁止删除、修改或上传照片，禁止导出私人照片内容。报告和留存日志不得包含私人照片内容或个人 GPS 数据。
- 分别标注已验证事实、静态推断和无法验证的事项，并为关键结论保留证据位置。

## 三、阶段一：设备及 vivo 相册组件识别

### 1. 设备环境

通过 ADB 确认 USB 调试连接和授权状态，记录实际设备型号、Android 版本、API Level、OriginOS 版本、Build Fingerprint 和安全补丁版本。

### 2. vivo 相册 APK 识别

通过设备实际查询确定相册真实包名，记录 APK 安装路径、版本名称、安装版本代码、是否拆分安装，以及相关系统服务包名。记录分析所用每个 APK 的版本和哈希。

### 3. 阶段输出

形成《设备及相册组件清单》，分别写入 `device-inventory.md` 和 `vivo-gallery-components.md`。

## 四、阶段二：ContentProvider 和系统接口调查

### 1. 检查 vivo 相册 Manifest

用 JADX 或 apktool 分析 APK，记录 `ContentProvider`、`Activity`、`Service`、`BroadcastReceiver`，以及 Provider 的 `authority`、`exported`、`readPermission`、`writePermission` 和自定义 `signature` 权限。

### 2. 检查 Provider 注册信息

结合 `dumpsys package`、`dumpsys activity providers`、APK Manifest 和系统可见的 Provider 注册信息交叉核对。重点搜索 `media`、`gallery`、`photo`、`album`、`location`、`geo`、`gps`、`map`、`place`、`travel`、`footprint`。

### 3. 测试可访问性

对候选 Provider 判断是否向第三方开放、是否要求系统权限或 vivo 签名、是否支持查询，以及可能提供的照片 URI、拍摄时间和 GPS 字段。仅对确认安全、公开或已获授权的接口开展有限量、只读测试。区分 ADB shell 的观察结果与普通第三方应用的实际权限。

### 4. 阶段输出

形成《vivo 相册 Provider 接口调查报告》，写入 `content-provider-analysis.md`。

## 五、阶段三：数据库及地点索引调查

### 1. APK 静态分析

在 JADX 中搜索 `latitude`、`longitude`、`gps`、`location`、`geo`、`place`、`coordinate`、`EXIF`、`MediaStore`、`SQLite`、`Room`、`ContentResolver`。检查照片 GPS 解析、地点聚合、数据库实体和 DAO、独立地点索引模块及数据库版本迁移。

### 2. 数据库结构推断

如果发现相关实现，记录静态代码或合法可访问信息中出现的数据库名称、表名、字段名、照片关联键、GPS 字段、地点字段、索引字段和数据更新机制。为每项记录注明证据，推测的名称标注为推测。

### 3. 数据访问边界

| 分类 | 判定 |
| --- | --- |
| A | 第三方应用可直接访问的数据库或接口 |
| B | 仅 vivo 自身可访问的私有数据库 |
| C | 需要系统签名或特权权限的接口 |
| D | 只能由静态代码推断、无法实际验证的数据结构 |

### 4. 阶段输出

形成《vivo 足迹地图数据存储结构分析》，写入 `vivo-location-index-analysis.md`。

## 六、阶段四：Android 标准媒体接口调查

对照 Android 官方文档和设备实际返回，确认 vivo 是否将照片 GPS 同步到标准媒体接口。

1. 核对 `MediaStore` 可读取的照片字段。
2. 核对 Android 10 及之后的 `LATITUDE`、`LONGITUDE` 字段状态，避免将已废弃字段当作可用方案。
3. 核对 `ACCESS_MEDIA_LOCATION` 的授权要求。
4. 核对 `MediaStore.setRequireOriginal()` 的作用、授权条件和可用范围。
5. 验证 `GENERATION_ADDED`、`GENERATION_MODIFIED` 与媒体库变更监听机制。
6. 判断能否在无需读取全部照片 EXIF 的情况下获得现有 GPS 信息。

形成《Android 标准媒体接口调查》，写入 `android-mediastore-analysis.md`。

## 七、阶段五：验证 GPS 索引复用可能性

### 方案 A：直接复用 vivo 公开接口

如果找到可访问的地点索引接口，设计只读验证程序，查询有限数量的照片记录，核对索引 GPS 与原始照片位置。检查设备重启后的接口稳定性，并观察媒体库正常新增或删除后的同步表现。遵守只读和隐私边界，无法观察的场景标注为未验证。

### 方案 B：复用 Android 标准接口

如果没有可用的 vivo 公开接口，但标准媒体服务能提供必要信息，验证第三方应用的权限条件和实际返回字段，评估是否需要补充读取 EXIF。

### 方案 C：本地一次性 EXIF 索引

如果前两种方案均不可行，评估首次扫描一次并将 GPS 解析结果存入本地 SQLite 的架构。之后通过 MediaStore 增量同步，避免重复读取已有照片的 EXIF，并处理权限变化、照片修改和删除。

三种方案的证据与评估结果写入 `reuse-feasibility.md`。

## 九、最终决策标准

最终报告必须逐项回答以下问题。

1. vivo 足迹地图的 GPS 数据来源是否已经确认？
2. GPS 是否仅存在于 EXIF？
3. 是否存在 vivo 独立 GPS 索引？
4. 是否存在第三方可访问的接口？
5. 是否能够直接读取已有地点索引？
6. 如果不能直接复用，最省资源的替代方案是什么？
7. 是否值得继续研究 vivo 内部实现？

最终结论四选一。

| 结论 | 判定 |
| --- | --- |
| A | 可以直接复用 vivo 现有 GPS 索引。 |
| B | 可以复用部分数据，需要 EXIF 补充。 |
| C | 无法复用 vivo 索引，采用一次性 EXIF 扫描 + 增量同步。 |
| D | 证据不足，需要进一步调查。 |
