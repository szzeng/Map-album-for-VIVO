# MAP-002 V3.1：vivo 原生 GPS 只读接入与安全性验证

## 一、任务背景

本项目是一款独立 Android 地图相册，主要运行于 vivo X300 Pro。

产品方向：

打开应用直接进入地图，利用照片已有 GPS 信息展示照片，支持地图缩放、照片聚合、区域照片浏览和照片查看。

本项目不是重新开发照片管理系统，而是重新实现照片的地图展示。

MAP-001 已完成 vivo 原生相册逆向调查，MAP-002 已完成部分实机探针测试。

目前已知：

1. vivo 原生相册存在 `gallery-mediaextra.db`，其中 `MediaExtraTable` 保存照片关联的 GPS 和时间等数据。
2. vivo 足迹地图存在读取该扩展表 GPS 的代码路径。
3. 找到候选接口：

   `content://com.android.gallery3d.dataprovider/mediaextra`

4. 该 Provider 使用 `normal` 权限。
5. 普通第三方应用已经成功获得权限并打开 Provider。
6. 合成 JPEG 测试已经验证 Provider 能返回与已知 GPS 匹配的记录。
7. 尚未验证真实图库 GPS 覆盖率、照片关联完整性、查询性能和原生服务并发安全性。

现有资料：
- `docs/research/`
- `map002-provider-probe/`

执行前必须审查最新提交和现有测试成果，避免重复验证。

## 二、最高优先级：不可改变的产品原则

### 1. 复用原生 GPS

直接使用 vivo 原生相册已经建立的 GPS 数据。

正式应用不得重新扫描所有照片提取 GPS。

不得因为开发方便而重新建立照片 GPS 索引。

### 2. 严格只读

应用只能读取：

- vivo GPS Provider。
- Android MediaStore。
- 用户授权范围内的照片 URI。

禁止：

- 向 vivo Provider 写入数据。
- 修改、删除 vivo 原生数据。
- 直接打开或修改 vivo 私有数据库文件。
- 修改 MediaStore。
- 新增、修改、删除任何照片。
- 通过 EXIF 重新提取 GPS。
- 建立持久化 GPS 数据库。
- 建立持久化照片位置关联表。

本任务后续真实图库测试必须完全只读。

此前合成照片测试仅作为历史技术验证保留，不得在真实图库验证中继续创建或删除测试媒体。

### 3. 不影响 vivo 原生相册

地图应用不能因为查询 GPS 而明显增加 vivo 原生相册的负担。

必须控制：

- 查询频率。
- 查询并发。
- Cursor 生命周期。
- 查询结果规模。
- 内存占用。
- CPU 和 I/O。
- SQLite 锁竞争。

只读不代表没有资源影响，必须进行实机验证。

### 4. 不重复建库

禁止建立第二套持久化 GPS 数据体系。

允许：
- 有容量上限的内存 GPS 缓存。
- 当前地图视口的临时结果。
- 临时照片关联关系。
- 临时聚合结果。

不允许：
- SQLite / Room GPS 索引。
- 持久化 GPS 缓存。
- 持久化 EXIF 解析结果。
- 用本地数据库代替 vivo 原生 GPS 数据源。

应用退出后，GPS 和照片位置关联缓存应释放。

## 三、阶段 A：审查现有技术成果

首先检查：

- MAP-001 最终报告。
- Provider 权限验证。
- 合成照片测试。
- MediaStore 单张读取测试。
- SQLite 能力测试。
- 现有 Provider 探针源码。

形成清单：

| 分类 | 处理方式 |
|---|---|
| 已经实机验证 | 保留证据，不重复测试 |
| 仅合成数据验证 | 明确标注，不扩大结论 |
| 尚未验证 | 纳入本次测试 |
| 与新只读原则冲突 | 停止相关实现 |

特别检查现有探针是否存在不必要的写入操作，确保真实图库验证路径完全不包含这些操作。

## 四、阶段 B：真实图库 GPS 数据验证

这是本次任务的核心。

### B1. 普通应用只读访问

使用普通第三方应用身份访问：

`content://com.android.gallery3d.dataprovider/mediaextra`

仅使用 `query()`。

验证：
- Provider 可用性。
- 权限授予情况。
- Cursor 返回情况。
- 实际记录数量。
- 必要字段是否存在。
- latitude、longitude 是否有效。
- 拍摄时间字段是否有值。

只投影必要字段，不查询不需要的媒体扩展数据。

### B2. 真实图库覆盖率

在用户当前授权范围内，统计：

- Provider 可访问记录数量。
- 有效 GPS 记录数量。
- 空 GPS 记录数量。
- 无效坐标数量。
- 图片与视频数量。
- 可关联 MediaStore 的记录数量。
- 无法关联的记录数量。

最终报告只保留统计数字和技术结论。

不输出真实 GPS、私人文件路径、照片内容和 EXIF 信息。

如果完整查询会造成较大负载，先进行小样本测试，再决定是否扩大查询规模。

不得为了统计覆盖率而读取原始照片 EXIF。

### B3. GPS 数据有效性

验证：
- 坐标是否为空。
- 纬度、经度是否在有效范围。
- 是否存在默认零值。
- 是否存在重复媒体记录。
- 不同媒体类型的 GPS 字段含义。

不允许直接把字段非空等同于坐标正确。

### B4. 拍摄时间

调查：
- `origin_date_taken`
- `origin_date_taken_exif`
- MediaStore `DATE_TAKEN`

明确字段来源、单位、时区和语义。

不能简单假设这些字段完全相同。

## 五、阶段 C：GPS 与照片的准确关联

GPS 能读取不代表地图能正确展示照片。

必须解决这一问题。

### C1. MediaStore 对应关系

验证 Provider `_id` 与以下信息的关联：

- MediaStore `_ID`。
- `volume_name`。
- 图片 Content URI。
- MIME 类型。
- 对应照片的缩略图。

特别检查：

1. 不同存储卷中相同 `_id` 的情况。
2. 内部媒体 ID 与 MediaStore ID 是否一致。
3. Provider 是否存在失效记录。
4. 删除照片后的关联状态。
5. 修改照片后的 GPS 更新情况。

不得将 `_data` 私有路径作为正式访问方式。

关联键必须经过实机验证，不能仅凭字段名称推断。

### C2. 照片权限

GPS Provider 返回记录后，还必须通过当前 MediaStore 授权范围验证对应照片是否可见。

处理：

- 全量照片授权。
- 部分照片授权。
- 用户重新选择照片。
- 照片权限撤销。
- 照片删除或 URI 失效。

未授权照片不得展示其 GPS 或照片内容。

### C3. 照片展示

通过 MediaStore 获取对应照片：

- 缩略图。
- 原图 URI。
- 照片拍摄时间。

验证读取速度和可用性。

本阶段不开发完整照片查看 UI。

## 六、阶段 D：查询能力与地图使用方式

必须确认 Provider 能否支持地图所需的查询模式。

检查：

1. Selection。
2. SelectionArgs。
3. 经纬度范围过滤。
4. 媒体 ID 查询。
5. 排序。
6. 分批读取。
7. Cursor 数据规模。

特别研究是否能够根据地图视口查询：

`latitude / longitude` 范围。

不能假设 Provider 支持空间索引，也不能假设经纬度过滤一定高效。

如果 Provider 只支持全量查询，应测量全量查询的耗时、内存占用和原生服务影响，再决定是否适合采用。

不要用高频小批次查询代替高效查询。

### 查询策略要求

- 单个后台查询 Worker。
- 有限并发。
- 查询请求合并。
- Cursor 及时关闭。
- 不在主线程访问。
- 查询有超时控制。
- 失败后停止重试。
- 地图移动时优先使用内存缓存。

## 七、阶段 E：原生服务保护

必须在真实 X300 Pro 上进行有限度验证。

### 测试场景

1. 原生相册空闲时查询。
2. 原生相册正常浏览时查询。
3. 原生相册正在处理新照片时查询。
4. 地图应用反复打开和关闭。
5. 查询过程中地图应用退出。
6. Provider 返回异常或超时。

### 观察指标

- Provider 查询耗时。
- 是否出现锁等待。
- 是否出现超时。
- Cursor 是否正常释放。
- 原生相册是否出现明显卡顿。
- 是否出现原生相册崩溃或 ANR。
- Provider 是否异常退出。
- CPU 和内存占用。
- 查询期间是否存在持续资源消耗。

不进行无限并发、持续高频轮询或故意诱发崩溃的压力测试。

### 安全策略

正式应用必须：

- 单 Worker 查询。
- 有限批量。
- 及时关闭 Cursor。
- 取消过期查询。
- 合并重复请求。
- 使用有容量上限的内存缓存。
- Provider 不可用时停止访问。
- 不持续自动重试。
- 不在后台长期轮询。
- 应用退出时释放全部查询资源。

如果无法证明查询负载可接受，应暂停采用该 Provider。

---

## 八、阶段 F：数据变化和内存缓存

### F1. 原生数据变化

验证以下场景：

- 相机拍摄新照片。
- 原生相册编辑照片。
- 原生相册删除照片。
- vivo 后台完成 GPS 索引。
- 手机重启。
- 地图应用重新启动。

研究 Provider 是否提供可靠的变化通知。

如果没有可靠通知：

- 不进行高频轮询。
- 地图重新进入时进行必要的轻量查询。
- 设置合理的内存缓存有效期。
- 用户主动刷新时重新读取。

不要求地图相册实时监控原生相册的每一次变化。

### F2. 内存缓存

允许在运行时保存：

- GPS 记录。
- 照片 ID 与 URI 的临时关联。
- 当前视口结果。
- 地图聚合结果。

要求：
- 容量有上限。
- 支持淘汰。
- 避免重复查询。
- 不持久化 GPS。
- 不建立本地数据库。
- 应用退出后释放 GPS 缓存。

不得为了地图流畅度偷偷建立第二套持久化 GPS 索引。

## 九、阶段 G：最终技术验证与决策

最终必须回答：

1. vivo Provider 是否能够读取真实图库 GPS？
2. 现有 GPS 覆盖率是多少？
3. 能否准确关联 MediaStore 照片？
4. 能否获取对应照片缩略图？
5. 是否支持地图视口范围查询？
6. 全量查询是否可接受？
7. 是否会影响原生相册正常工作？
8. 是否存在锁竞争或明显资源负担？
9. 是否能正确处理照片删除和授权变化？
10. 是否能够完全不建立第二套 GPS 数据库？

### 验收标准

| 项目 | 通过要求 |
|---|---|
| 数据访问 | 普通应用合法只读 |
| GPS | 真实图库有有效记录 |
| 覆盖率 | 有实际统计，满足地图使用要求 |
| 照片关联 | ID、存储卷、URI 对应可靠 |
| 照片访问 | 能获得授权范围内的照片 |
| 查询性能 | 满足地图交互要求 |
| 并发影响 | 无明显原生服务负面影响 |
| 数据更新 | 能合理处理新增、修改、删除 |
| 只读 | 无任何原生数据写入 |
| 不重复建库 | 不建立持久化 GPS 数据库 |
| 资源管理 | Cursor、查询任务和内存缓存正确释放 |

### 否决条件

出现以下任一问题，暂停进入 MAP-003：

- 无法读取真实图库 GPS。
- GPS 与照片关联不可靠。
- GPS 覆盖率不足以支持产品目标。
- 查询负载明显影响 vivo 原生服务。
- 只能依赖高频全量查询。
- 权限或接口稳定性无法接受。

不得自动切换 EXIF 全量扫描。

不得擅自改变只读复用原则。

必须提交证据和替代方案，等待用户决定。

## 十一、执行边界

本次任务只做数据访问验证和最小数据层原型。

不开发地图 UI，不引入地图 SDK，不开发照片时间线、旅行记录和 AI 功能。

执行前先检查现有成果，按阶段推进，不重复已经完成的验证。

每个阶段汇报实际结果，区分已验证、推断和未知。

如果关键条件不满足，停止并报告，不得自行改变产品技术原则。

完成后提交代码、报告和最终技术决策，等待用户确认 MAP-003。
